# 解析方法

## 目的

この文書は、CoDrone EDU の PID 制御ログを毎回同じ観点で評価し、修正と再実験を再現可能にするための解析手順書である。

最終目標を改定する:
・PID制御で指定した値(最終的には、x, y,zに指令値送る)だけ移動する.風の影響や、物理的な妨害や干渉を受けても、厳密に、精密に目的の分だけ最速で移動するようにする.
・理論上、最速を目指す.すべての動作を、精密に、最速で行うようにする。最速を最優先事項とする。最高速で進み、急ブレーキで止まるようにしたい
・堅牢性、保守性を最大限に高める


## 対象ログ

主に以下を使う。

- `flight_logs/pid_flight_*.jsonl`
  - 1 回の飛行実験ごとの逐次ログ
- `flight_logs/latest_run.log`
  - 人間が目で追いやすいテキストログ
- `flight_logs/last_pid_profile.json`
  - 最新 PID プロファイル
- `flight_logs/last_pid_profile_2000mm.json`
  - 長距離向け PID プロファイル
- `flight_logs/last_history_analysis.json`
  - 直近複数回の要約

## JSONL ログの基本構造

ログには主に 3 種類のイベントが入る。

1. `metadata`
   - ドキュメント URL や使用 PID プロファイルを記録する。
2. `sample`
   - 各制御周期ごとの状態とコマンドを記録する。
3. `summary`
   - 1 回の飛行全体の要約を記録する。

## sample で見る項目

毎回必ず見る項目:

1. `error_x_mm`
2. `error_y_mm`
3. `error_z_mm`
4. `error_yaw_deg`
5. `x_velocity_mm_s`
6. `y_velocity_mm_s`
7. `z_velocity_mm_s`
8. `pitch_cmd`
9. `roll_cmd`
10. `throttle_cmd`
11. `yaw_cmd`
12. `pos_fresh`
13. `motion_fresh`
14. `stale_cycles`

## summary で見る項目

毎回必ず記録する項目:

1. `final_error_x_mm`
2. `final_error_y_mm`
3. `final_error_z_mm`
4. `final_error_yaw_deg`
5. `duration_sec`
6. `peak_speed_x_mm_s`
7. `peak_speed_y_mm_s`
8. `peak_speed_z_mm_s`
9. `stale_ratio`
10. `oscillation_count_x`
11. `oscillation_count_y`
12. `oscillation_count_z`
13. `settling_time_sec`

## 解析の手順

## 手順 1. まず summary を読む

最初に全体結果を確認する。

評価観点:

- 目標地点に到達したか
- `x/y/z` のどこで誤差が残ったか
- 時間がかかりすぎていないか
- 振動回数が多すぎないか

判定の目安:

- 良好:
  - `|x誤差| <= 10mm`
  - `|y誤差| <= 15mm`
  - `|z誤差| <= 15mm`
  - `duration_sec` が過去最良に近い
- 要改善:
  - いずれかが 30mm を超える
  - `oscillation_count_* >= 3`
  - `stale_ratio > 0`

## 手順 2. 誤差時系列を見る

`sample` を時系列で追い、誤差がどう変化したかを見る。

見るポイント:

1. `error_x_mm` が単調に減っているか
2. `error_x_mm` が 0 をまたいで大きく往復していないか
3. `error_y_mm` が途中で増大していないか
4. `error_z_mm` がゆっくりズレ続けていないか

解釈の目安:

- 誤差が減らず横ばい:
  - `kp` 不足または `min_output` 不足
- 誤差が急に反転して往復:
  - `kp` 過大または `kd/kv` 不足
- 徐々にズレ続ける:
  - `ki` 不足、または外乱に勝てていない

## 手順 3. 速度を見る

位置だけではなく速度を必ず見る。

見るポイント:

1. 目標付近で `x_velocity_mm_s` が十分落ちているか
2. `y_velocity_mm_s` が大きいまま横流れしていないか
3. `z_velocity_mm_s` が小刻みに符号反転していないか

解釈の目安:

- 目標付近でも速度が高い:
  - `kv` または `kd` が不足
- 速度は低いが誤差が消えない:
  - `kp` または `ki` が不足

## 手順 4. コマンド飽和を確認する

`pitch_cmd`, `roll_cmd`, `throttle_cmd`, `yaw_cmd` が長時間大きい値に張り付いていないかを見る。

見るポイント:

1. 出力上限近くに長く張り付くか
2. 小さい値のまま動かず停滞していないか

解釈の目安:

- 張り付きが長い:
  - 目標に対し保守的すぎる可能性もあるが、外乱で押し戻されている可能性もある
- 小さすぎて動かない:
  - `min_output` の引き上げ検討

## 手順 5. センサ鮮度を見る

`pos_fresh`, `motion_fresh`, `stale_cycles` を必ず確認する。

見るポイント:

1. `pos_fresh=0` が連続していないか
2. `stale_cycles` が繰り返し増えていないか

解釈の目安:

- `stale_cycles` が継続的に増える:
  - 通信更新やセンサ更新に問題がある可能性
  - 制御器だけを触っても改善しない可能性がある

## 手順 6. 外乱耐性を見る

風や軽い手動妨害を加えた実験では、外乱直後を重点的に見る。

見るポイント:

1. 誤差がどれだけ増えたか
2. 何秒で回復したか
3. 回復時に振動が増えていないか

判定:

- 良い回復:
  - 誤差増大後、短時間で単調減少に戻る
- 悪い回復:
  - 反対側へ大きく行き過ぎる
  - `y` や `z` が連鎖して悪化する

## 変更判断ルール

ログを見て次のように判断する。

## 1. `kp` を上げるべきケース

- 誤差が大きく残る
- コマンドが飽和していない
- 目標付近で鈍い

## 2. `ki` を上げるべきケース

- 外乱後に一定量のズレが残り続ける
- 長時間たっても最後の数 cm が消えない

## 3. `kd` を上げるべきケース

- 目標をまたぐ往復が多い
- 停止直前に揺れ続ける

## 4. `kv` を上げるべきケース

- 速度が落ちずに突っ込みやすい
- 高速進入後の戻りが大きい

## 5. `min_output` を上げるべきケース

- 小誤差帯で動かなくなる
- 誤差が残るのにコマンドが弱くて進まない

## 毎回の解析記録テンプレート

実験ごとに最低限これを書く。

```md
## 実験名

- ログ:
- 条件:
- final_error_x_mm:
- final_error_y_mm:
- final_error_z_mm:
- final_error_yaw_deg:
- duration_sec:
- stale_ratio:
- 目視した主な挙動:
- 原因推定:
- 次回変更方針:
- 次回推奨試験距離:
```

## 重要な注意

1. 1 回だけ良い結果が出ても、その値を正解と見なさない。
2. 最低 3 回以上同条件で飛ばし、再現性を見る。
3. `x` だけ良くても `y` や `z` が悪化していたら改良とは見なさない。
4. 最速化を狙うときも、必ず安全停止条件とセンサ停滞を確認する。
5. 強風・接触外乱を入れる試験は、通常試験で安定してから段階的に行う。

## 次回推奨試験距離の決め方

毎回の解析結果に基づいて、次に飛ばす推奨距離を必ず 1 つ書く。

基本方針:

- 距離は「最終目標に最短で近づくための切り分け手段」として決める。
- いきなり長距離固定にはしない。
- まずセンサ鮮度、停止性、短距離での進行方向の整合性を確認し、その後で距離を伸ばす。

## 符号についての前提

このプロジェクトでは、CoDrone EDU の軸方向は工業製品として固定であり、飛行中に自動推定しない前提を採用する。

運用ルール:

- `pitch/roll/throttle/yaw` の符号は固定値を使う。
- 飛行中のログから符号を自動反転しない。
- 進行方向がおかしい場合は、まずコードや座標解釈のバグとして調べる。
- 問題切り分けのために短距離試験を提案することはあるが、それは符号学習のためではなく、挙動確認のためである。

## 推奨距離のルール

## 1. センサ更新が悪いとき

条件:

- `stale_ratio > 0.30`
- または `stale_cycles` による安全停止が発生

推奨距離:

- `200mm` から `400mm`

理由:

- 長距離で評価しても、制御器ではなくセンサ更新問題が支配的になるため。
- 短距離で位置更新と符号の整合性を先に確認したほうがよい。

## 2. 進行方向が期待と逆に見えるとき

条件:

- `error_x_mm` が時間とともに増える
- 目標へ向かうはずのコマンドで逆方向へ離脱する

推奨距離:

- `300mm` 前後

理由:

- 長距離で評価しても原因切り分けが難しいため。
- 必要なら `+300mm` と `-300mm` を別々に試す。

## 3. 到達はするがオーバーシュートが大きいとき

条件:

- `x` は目標付近まで行く
- ただし往復や振動が多い

推奨距離:

- 現在距離の `0.5` 倍から `0.75` 倍

理由:

- 近距離で停止性を詰めたほうが、長距離の最速化にも効く。

## 4. 短距離が安定したとき

条件:

- 少なくとも 3 回連続で
  - `|final_error_x_mm| <= 20`
  - `|final_error_y_mm| <= 20`
  - `|final_error_z_mm| <= 20`
  - `stale_ratio <= 0.10`

推奨距離:

- 現在距離の `1.5` 倍から `2.0` 倍

例:

- `300mm` が安定したら `500mm` か `600mm`
- `500mm` が安定したら `800mm` か `1000mm`
- `1000mm` が安定したら `1500mm` か `2000mm`

## 5. 最終目標に近い長距離検証をするとき

条件:

- 中距離までの再現性がある
- 符号反転や高 stale がない

推奨距離:

- `1500mm` から `2000mm`

理由:

- この段階で初めて「最速化」と「外乱耐性」の長距離評価をする意味が大きい。

## 今回の基準に当てはめた推奨

`pid_flight_20260630_164659.jsonl` に対しては次を推奨する。

- 次回推奨試験距離: `300mm` または `400mm`

理由:

- `stale_ratio = 0.7024`
- `x` 誤差が増大
- 主進行方向が期待と逆に見える区間がある

この状態では長距離最適化より先に、短距離で位置更新と進行方向の整合性を切り分けるべきである。

## 追加: stale 判定の見方

`stale_ratio` が高いだけで即座に「制御失敗」とは判断しない。以下を同時に見る。

- `x_mm`, `y_mm`, `z_mm` が目標へ近づいているか
- stale 発生中でも `final_error_*` が縮小しているか
- 停止理由が「物理的な逆進」なのか「安全停止条件が厳しすぎた」のか

今回の `pid_flight_20260630_170026.jsonl` では:

- `stale_ratio = 0.8056`
- しかし `x_mm` は `-43.64 -> 8.16` と目標方向へ進行
- 停止直前も `final_error_x_mm = 45.47` まで縮小

したがって、この種のログは「符号誤り」より先に「位置更新周期に対して stale 判定が厳しすぎる」と読む。

## 追加: 次回の推奨試験距離の決め方

毎回の提案は、以下の順で決める。

1. まず「方向確認」か「到達率改善」かを決める
2. 方向確認なら `100mm` から `150mm`
3. 到達率改善なら、直前に誤差が半減した距離を再試験する
4. `|final_error_x_mm| <= 20` が見えたら `1.5` 倍から `2.0` 倍へ延ばす

今回の基準:

- 目的は方向確認ではなく、stale 条件修正後の到達率改善確認
- そのため次回は `100mm` 再試験を第一候補、`150mm` を第二候補とする

## 追加: 反対方向へ進んだときの判定基準

以下の 3 つが同時に成り立つ場合、主因は stale ではなく符号誤りと判断する。

- `stale_ratio` が低い
- `error_x_mm` が増加し続ける
- `pitch_cmd` を出すたびに `x_mm` が目標と逆向きへ離脱する

今回の `pid_flight_20260630_170651.jsonl` では:

- `stale_ratio = 0.0370`
- `error_x_mm = 95.79 -> 2415.33`
- `pitch_cmd < 0` の継続中に `x_mm = -57.58 -> -2377.12`

このため、「更新遅延ではなく pitch 符号誤り」と判定する。

## 追加: 今後の安全判定

次回以降は、単に誤差を見るだけでなく、初動の逆走を安全条件として監視する。

- 短距離指令時は開始直後の `pitch_limit` を低くする
- `|error_x_mm|` が初期値より大きく悪化し続けたら即停止する

これは符号を推定するためではなく、壁衝突を避けるための安全停止である。

## 追加: 上下振動の見分け方

高度軸の問題は、以下の並びで判定する。

- `error_z_mm` が 10 から 50mm の範囲でも `throttle_cmd` が大きく正負反転する
- `z_velocity_mm_s` が正負に大きく振れる
- `peak_speed_z_mm_s` が過大なのに `final_error_z_mm` が残る

今回の `pid_flight_20260630_171035.jsonl` では:

- `peak_speed_z_mm_s = 78.95`
- `final_error_z_mm = 26.56`
- `error_z_mm ≈ 20` で `throttle_cmd = -20`
- その直後に `error_z_mm ≈ 30` で `throttle_cmd = +18`

このため、「推力不足」ではなく「近距離の高度制御が強すぎる」と読む。

## 追加: 高度軸の修正指針

高度軸に上下反復が見えたら、優先順位は次の通り。

1. `throttle.min_output` を疑う
2. 目標近傍の `throttle_limit` を下げる
3. `z_velocity` に対するブレーキを強める
4. それでも残る場合にのみ `kp/ki` を調整する

次回の推奨距離:

- この症状では `100mm` を維持する

理由:

- 今は `x` 距離を伸ばすより、`z` の整定を先に収束させる方が切り分けとして有効である。
